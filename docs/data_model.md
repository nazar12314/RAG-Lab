# Dataset and data model

The lab uses one synthetic corpus, **engineering-ops-v1**: the operational knowledge of a
fictional e-commerce company, *Kestrel Commerce*, from April to October 2026. Everything
(records, documents, graph, gold labels) is generated from a single hand-authored
**canonical fact model**, so every answer can be traced back to its source.

## Contents

| Asset | Count | Notes |
| --- | --- | --- |
| Services | 20 | 7 subsystems, 7 teams, 2 external providers (PayNova, MailRelay) |
| Dependencies | 35 | 4 change over time (fraud-scoring move on 1 Jun, event-bus migration on 5 Aug) |
| Deployments | 87 | releases, hotfixes, 10 rollbacks, config changes, infra upgrades |
| Incidents | 38 | 4 SEV1, 12 SEV2, 14 SEV3, 8 SEV4; 26 triggered by a deployment |
| Documents | 138 | tickets, postmortems, release notes, ops reviews, runbooks, architecture, ADRs, distractors |
| Facts | 490 | atomic gold facts with document spans and record sources |
| Curated graph | 161 entities, 330 relations | every relation has evidence |
| Benchmark | 80 questions | 20 showcase / 30 development / 30 held-out; all 9 categories in every split |

`data/seed/engineering-ops-v1/manifest.json` holds exact counts and the corpus hash.

## Directory layout

```txt
data/seed/engineering-ops-v1/
  canonical/            GOLD  hand-authored source of truth (YAML + authored markdown)
  corpus/               retriever-facing business records (JSONL) and documents (JSONL + .md)
  graph/curated/        retriever-facing curated graph (upper-bound baseline)
  manifest.json
data/benchmark/engineering-ops-v1/
  questions.yaml        GOLD  hand-authored questions
  *.jsonl               GOLD  generated facts, fact sources, entity mentions, question labels
backend/app/dataset/    generator, validator and loader
```

Everything except `canonical/` and `questions.yaml` is generated by `make dataset` and
committed, so a classroom setup can seed without rebuilding. `make dataset-check` (and a
unit test) fails if the committed files are stale.

## Workflow

```bash
make db && make migrate   # PostgreSQL + schemas + retriever role
make seed                 # reset and load corpus, curated graph and gold labels
```

To change the data: edit `canonical/` or `questions.yaml`, run `make dataset`, commit the
regenerated files. The build validates chronology, rollback versions, references, fact
coverage, relation evidence, and every benchmark label against the facts and the graph.

## Database layout

Four PostgreSQL schemas separate the parts of the system by who may read them.

| Schema | Readable by retrievers | Contents |
| --- | --- | --- |
| `corpus` | yes | business records and source documents |
| `search` | yes | index profiles, chunks, embeddings, FTS vectors |
| `graph` | yes | versioned graphs (curated / extracted) with provenance |
| `eval` | **no** | gold facts, benchmark labels, experiment history |

The migration creates the `raglab_retriever` role with `SELECT` on `corpus`, `search` and
`graph` only. Retrievers and agent tools should run with `SET ROLE raglab_retriever`; any
read of `eval` then fails with `permission denied`, making the no-leakage rule enforceable
rather than a convention.

### corpus

| Table | Key columns |
| --- | --- |
| `dataset_versions` | id, as_of, period, corpus_hash (one loaded snapshot per database) |
| `subsystems`, `teams`, `external_systems` | reference data |
| `services` | id, slug, name, subsystem_id, team_id, tier |
| `service_dependencies` | service_id DEPENDS_ON (depends_on_service_id \| depends_on_external_id), type, criticality, valid_from, valid_to |
| `deployments` | id, service_id, version, kind, deployed_at, status, rolls_back_deployment_id, change_summary |
| `incidents` | id, primary_service_id, severity, status, cause_category, started/detected/mitigated/resolved_at, summary |
| `incident_services` | incident_id, service_id, impact_type (primary / degraded / downstream) |
| `incident_deployments` | incident_id, deployment_id, association_type (caused / suspected / ruled_out / remediation / follow_up), verified_source_document_id |
| `documents` | id, title, doc_type, created_at, source_uri, content, content_hash, metadata |

Dependency direction is explicit (`service_id` depends on the target) to avoid the usual
upstream/downstream ambiguity. Validity intervals are `[valid_from, valid_to)`.

### search

| Table | Key columns |
| --- | --- |
| `index_profiles` | id, chunker, chunker_config, embedding_model, embedding_dim, status, chunk_count, content_hash |
| `document_chunks` | index_profile_id, document_id, ordinal, text, span_start, span_end, section_path, embedding vector(1536), tsv (generated) |
| `chunk_entities` | chunk_id, entity_id, span, mention_text |

These tables are filled by the indexing pipeline, not by the seed. Chunk spans are character
offsets into `corpus.documents.content`, which is what makes chunking strategies comparable.
`tsv` is a generated column with a GIN index, so FTS can never drift from chunk text.

### graph

| Table | Key columns |
| --- | --- |
| `graph_versions` | id, kind (curated / extracted), extractor_model, extractor_config, index_profile_id |
| `entities` | graph_version_id, key, entity_type, canonical_name, external_ref |
| `entity_aliases` | entity_id, alias, alias_norm (generated, indexed) |
| `relations` | graph_version_id, key, source_entity_id, target_entity_id, relation_type, confidence, verified_status, valid_from, valid_to |
| `relation_evidence` | relation_id, evidence_kind (document / record), document span or chunk, record_table/record_id |

Curated relation types: `DEPENDS_ON`, `OWNED_BY`, `PART_OF`, `DEPLOYED_TO`, `ROLLS_BACK`,
`AFFECTED_BY` (service to incident), `TRIGGERED_BY`, `RESOLVED_BY`, `ROOT_CAUSE_IN`, and
`SUSPECTED_TRIGGER` with `verified_status = 'refuted'` for releases that were ruled out.
Entity keys are stable ids (`SVC-CHECKOUT-API`, `INC-104`, `DPL-010`, `TEAM-PAYMENTS`), so
an extracted graph can be scored against the same keys.

### eval

| Table | Purpose |
| --- | --- |
| `facts` | atomic canonical facts (`F-INC-104-TRIGGER`, `F-LINK-06`, ...) |
| `fact_sources` | document spans or records stating each fact, with stance: supports / preliminary / contradicts |
| `entity_mentions` | gold entity mentions per document span (for entity linking / extraction eval) |
| `relation_facts` | curated relation to fact mapping (path correctness) |
| `questions` | question, split, category, reference answer, accepted answers, answer type, answerable |
| `question_evidence` | required / supporting facts per question |
| `question_documents` | acceptable documents for document-finding questions |
| `question_paths` | expected graph paths as entity-key steps |
| `question_tools` | human-labeled suitable tools and first tools |
| `experiment_runs`, `experiment_results` | frozen configurations and per-question results |

Gold labels reference **facts, not chunks**. To score a retriever, map each retrieved chunk
to the facts whose `fact_sources` spans overlap it (stance `supports`), then compute
recall@k and complete-evidence rate on fact ids. Keep chunk-level and fact-level precision
in separate charts.

Experiment tables reference questions, index profiles and graph versions by plain id (no
foreign keys), so reseeding never deletes experiment history.

## Built-in difficulty

The corpus is deliberately imperfect, so that no single retriever wins everywhere:

- **Aliases and name clashes:** `payment-service` (legacy) for Payments API; "warehouse" means
  both Warehouse Sync (stock) and Warehouse Loader (analytics); documents use varying aliases.
- **Lexical distractors:** a staging load test about pool exhaustion that outranks the real
  INC-104 postmortem in FTS; offsite notes about the hotel *pool* and a *talent pool*.
- **Near-miss deployments:** INC-104, INC-113, INC-123 and INC-137 each have a release that
  shipped shortly before and was ruled out.
- **Temporal dependencies:** fraud scoring moved from Checkout to Payments on 1 June; the
  Checkout architecture overview is stale and still shows the old design.
- **Conflicting sources:** tickets and ops reviews record early hypotheses (stance
  `preliminary`); postmortems are authoritative.
- **Imperfect records:** INC-131 is recorded under the wrong primary service; two causal
  deployment links are missing from `incident_deployments`; two refuted suspects remain
  "suspected" in the tracker.
- **Synonyms:** connection pool exhaustion, pool depleted, database saturation, too many
  connections.
- **Unanswerable questions:** no approval records, revenue figures, incident roles or phone
  numbers exist; INC-136 has no determined root cause.
